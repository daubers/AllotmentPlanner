# Allotment Planner: Implementation Plan

## Context
A multi-user app to map an allotment, plan and log work as tasks pinned to map features, print a daily todo list, upload progress photos with a historical timeline, post activity to a Mastodon account, and show a progress overview ("feel good" dashboard). A measuring checklist, filled in on site, corrects the drawn map to real-world dimensions.

Decisions: Leaflet + Geoman map editor; OpenSfM + GDAL for photo/video → orthomap; ActivityPub via posting to an existing Mastodon account through its API; multi-user with roles. Stack: Flask / Celery / Postgres (PostGIS) with OpenAPI; TypeScript + React frontend. Docker compose for test instances; Gitea Actions for CI (see [ci.md](ci.md)).

Tickets live in YouTrack project **AM** (Allotment Manager) at pm.daubney.dev. Workflow: one feature branch per ticket (`AM-<n>-short-name`), small regular commits, merge to `main` when tests pass.

## Backend design
- **Flask + flask-smorest** (marshmallow schemas → OpenAPI 3 at `/api/openapi.json`, Swagger UI at `/api/docs`). Source of truth for the frontend client.
- **SQLAlchemy 2 + Alembic**, Postgres with **PostGIS** (`postgis/postgis`); geometries as `geometry(…, 4326)` via GeoAlchemy2. Leaflet works in lat/lng, so no local-canvas coordinates. Alembic autogenerate ignores tables we don't own (`include_object` in `extensions.py`).
- **Celery + Redis**: media processing (EXIF, thumbnails), photogrammetry, Mastodon posting, daily rollups.
- **Auth**: Flask-JWT-Extended, argon2 hashes. Roles per allotment through memberships: `owner`, `editor`, `viewer`.
- **Storage**: `allotment/storage.py` with two backends behind one interface: plain files on a shared Docker volume (default; used by compose and tests) or any S3-compatible service (`STORAGE_BACKEND=s3`, tested against moto). MinIO was dropped: its container images are no longer published. Orthomaps will be stored as COG GeoTIFF + XYZ tiles.

### Data model
`User`, `Allotment`, `Membership(user, allotment, role)` (done). Planned: `MapFeature` (allotment, kind: bed/path/shed/tree/etc., geometry incl. polygon/point/line, circle as point + `radius_m`, name, style jsonb), `MapLayer` (generated ortho: status, source job, bounds, tile URL), `Task` (title, description, status todo/doing/done, due date, priority, recurrence, assignee, optional `feature_id`, optional point geometry, completed_at/by), `Media` (kind photo/video, storage key, EXIF taken_at, lat/lng, heading, optional `feature_id`/`task_id`, caption), `MapJob` (input media, status, OpenSfM log, output layer), `ActivityLog` (event type, actor, subject refs, timestamp: feeds overview and Mastodon), `MastodonAccount` (instance URL, encrypted token, per-allotment, visibility), `Measurement` (allotment, kind edge|diagonal|radius|custom, endpoint A/B as feature + corner index, `value_m`, note, skipped, stale, measured_by/at) and `Allotment.length_unit` (`m`|`cm`|`ft_in`; values are always stored in metres).

### API (all under `/api/v1`)
Done: auth (register/login/refresh/me), allotments + members.
Planned: features (CRUD, GeoJSON in/out, bulk `PUT` of a FeatureCollection), tasks (CRUD, filter by date/feature/status, complete/uncomplete), media (presigned upload + register, list by feature/date), map-jobs (create from media ids, poll status), layers, timeline (media by date for compare), overview (per-day/week counts of tasks done, photos added, features changed + streak), printable todo (`GET /todo?date=` → HTML/PDF), Mastodon settings + test post, measurements (`GET` list with the drawn length of each item, `PATCH` value/note/skip, `POST` a custom corner-to-corner distance, `POST /sync` to generate or refresh the checklist, `POST /fit?preview=true|false` to preview or apply the corrected geometry).

### Key flows
- **Map from media**: user uploads photos/videos → Celery extracts EXIF GPS/heading/time (piexif/exifread; ffmpeg samples video frames, `ffprobe` location tags) → `MapJob` runs OpenSfM with GPS priors → GDAL (`gdalwarp`/`gdal2tiles`) orthoprojects to a georeferenced GeoTIFF + tiles → `MapLayer` shown as an overlay. Media without GPS can be placed manually by dragging on the map. The user then traces features over the layer (Geoman).
- **Daily todo**: print-optimised HTML (`@media print`) listing due/overdue tasks grouped by bed, with a small map snapshot; WeasyPrint as optional PDF endpoint.
- **Mastodon**: on task complete / photo upload / milestone, a Celery task posts a status (with media) using `Mastodon.py`; opt-in per event type, with a daily-digest option.
- **Progress overview**: aggregate `ActivityLog` by day/week; heatmap calendar, streak, "this week you completed N tasks", newest progress photos.
- **Measuring checklist** (phase 11): items are generated from the drawn features: a polygon with n corners gets its n edges plus a fan of n-3 diagonals from corner 1 (2n-3 distances fix a shape exactly), a line gets one item per segment, a circle one radius item. Sync is idempotent: unmeasured items whose corners vanished are deleted, measured ones are kept and flagged stale. **Fit**: project lon/lat to local metres about the allotment centroid, then Gauss-Newton least squares (numpy) per connected group of features, minimising `|p_i - p_j| - d` plus a weak prior toward the drawn positions, which pins translation, rotation and mirroring to what was drawn. The result reports residuals before and after, flags probable mismeasurements (residual over 0.15 m), says how many more measurements an under-determined shape needs, and goes through the existing feature validation (e.g. no self-intersection) before anything is written. Preview never writes; apply is one transaction.

## Mobile app (planned, AM-27 to AM-31)
The mapping pipeline is only as good as what it is fed. Real phone sets so far had a GPS fix that never updated, shots about 10 s apart with too little overlap to chain together, and no measured distance to pin the scale. A native field app fixes the inputs rather than the algorithms. **Expo / React Native + TypeScript** (Expo Router, EAS builds), talking to the same API with types generated from the same OpenAPI document; tokens in secure storage; an SQLite write queue so everything works without signal (idempotent writes, retry with backoff, resumable uploads). Backend additions are small: optional `lat`, `lng`, `heading`, `taken_at` and `capture_session` on `POST /media` (stored with `Media.position_source` = `exif`|`device`|`manual`; device values beat EXIF and are trusted by `prepare_dataset`), the measurement endpoints of phase 11, and `POST /allotments/{id}/boundary-trace`.
- **Guided capture**: reads GPS (fresh, high accuracy, shown in metres), compass heading and tilt itself and sends them explicitly, so a stale EXIF fix cannot poison a job. Coaching comes from the failures seen on real photos: step between shots, tilt and blur warnings, keep the fence in view, a coverage strip of headings and distance walked, a session summary, and "Build map from this session".
- **Measure**: the phase 11 checklist as a phone screen (numbered corner sketch, decimal keypad, unit parser, preview/apply). An AR tape measure is a later option.
- **Walk the boundary**: record the phone's GPS while walking the fence line, with corner pins; the server fits lines (reusing `boundary.py`) or takes the pinned corners and creates a "Plot boundary" `MapSuggestion`, so the existing review and accept flow applies it.
- **Tasks and quick photos**: today's tasks with optimistic tick-off, tasks at the current position or on a feature, photos attached to features or tasks, a read-only map.
Gitea CI gets a `mobile` job (typecheck, lint, jest); EAS builds are manual (`docs/mobile.md`). Out of scope for now: app store distribution, DJI and Android video telemetry, AR measuring, background upload on iOS beyond what the OS grants.

## Seeds, trays and plantings (planned, AM-38 to AM-44)
What is being grown, not just what is being done. A **seed library** is filled by photographing the back of a packet; **trays** hold sown seeds (several kinds per tray) with photos and a link back to each packet; **plantings** record what is in each bed and where, whether it was direct sown or planted out from a tray. Trays and beds each need an editor because each holds many kinds of plant. Decisions: packets are read by a **local vision-language model** on the mapper (photos stay on the server), the calendar graphic is read **from pixels**, positions in a bed are **drawn regions**, trays are **cell grids**, and tasks are **suggested** from sow dates.

**Data model.**
- `SeedPacket`: allotment, `status` (draft | active), name, variety, supplier, latin name, notes, sow depth (mm), spacing between plants and rows (cm), days to germinate (min, max), days to maturity (min, max), sun, `stock` (full | part | low | empty), best-before year, raw text read from the packet, and `calendar` `{sow_indoors, sow_outdoors, plant_out, harvest}`, each a list of months 1 to 12. Front and back photos are `Media` rows linked by `packet_id`.
- `PacketScan`: a reading job like `MapJob` (media, status, log, result with a confidence per field, the calendar crop). It produces a **draft** packet to review, never an active one.
- `Tray`: allotment, name, rows x cols, tray type label, sown date, location text, notes, status (active | planted out | finished). `TrayCell`: tray, row, col, packet, count, sown and germinated dates, status (empty | sown | germinated | failed | planted out), note, and the planting it went into; unique per tray, row, col.
- `Planting`: bed (a `MapFeature`), packet, a **region** polygon validated to lie inside the bed, count, method (direct sow | transplant), the source tray and cells when transplanted, sown / planted / harvested dates, status (sown | growing | harvesting | finished | failed), notes. Regions may overlap (inter-planting), with a warning.
- `Media` gains `packet_id`, `tray_id`, `planting_id`; `Task` gains `tray_id`, `planting_id`, so photos, the timeline, Mastodon posts and the daily list work unchanged.
- Events `packet.created`, `packet.scanned`, `tray.created`, `planting.created`, `tray.planted_out`, `planting.harvested` are recorded in `ActivityLog`, with a new "sowings" overview counter.

**Plant out is one transaction**: `POST /trays/{id}/plant-out` takes cells, a bed, a region and a date, creates one `Planting` per packet among the cells, marks the cells planted out pointing at it, all or nothing (422 with the reason if the region is outside the bed). A direct sow is `POST /beds/{feature_id}/plantings`.

**Reading a packet.** Runs on the mapper (a new `vision` Celery queue; the model is downloaded into the `models` volume on first use, like Grounding DINO, because the registry limits layer size). (1) A small local VLM (candidate Qwen2-VL-2B-Instruct; fallback Florence-2 plus OCR with rules if CPU speed or accuracy disappoints) returns the text fields as JSON plus the location of the calendar and its legend. (2) `calendar_cv.py` reads the calendar from pixels, because a language model is unreliable at "which months is this bar over": crop it, find the 12 month columns from the header labels (J F M A M J J A S O N D, Jan to Dec, or 1 to 12) and the rows by horizontal projection, average the colour of each cell, cluster colours (background = most common) and match each cluster to a legend entry by swatch colour or row label. (3) The result opens as a **draft**: the calendar crop beside a 12-month editor per activity (tap months), every field editable, low-confidence fields highlighted. (4) A **spike comes first** (AM-39): an evaluation over 10 to 15 of the user's real packets, kept in scratch and deleted afterwards, reporting per-field and calendar accuracy and seconds per packet; the pipeline is only built if it is usable, otherwise the approach changes and that is said plainly.

**Suggested tasks** (`task_suggestions.py`, pure): from a packet, a sow date and today: check germination at the packet's minimum days, prick out (about three weeks after sowing unless the packet says otherwise), harden off and plant out inside the plant-out months, thin, harvest at the start of the harvest window or by days to maturity. Listed and accepted in one step onto the task list, pinned to the tray or bed, all or nothing like map suggestions.

**Screens.** Web: Seeds (library, search, "what can I sow this month?"), packet detail (fields, 12-month strip, photos, every tray and bed using it), add packet (upload, wait, review the draft), **tray editor** (select cells, assign a packet and count, mark germinated or failed, photos, plant out), **bed editor** (the bed's sketch, draw a region, pick a packet, direct sow or from a tray, plantings with status and dates, photos), plantings drawn as labelled regions in their beds on the map. Mobile: scan a packet, browse the library, tray grid with quick actions, a bed's plantings, photos; region drawing and plant out are built on web first.

**Reuse.** The detector's lazy-model pattern and `models` volume; mapper queue routing; `MapJob` for `PacketScan`; the map-suggestion accept flow for task suggestions; media upload and signed URLs; the mobile offline queue and capture screen; `measure.py` projection helpers and the mobile sketch maths for region geometry; the UI kit.

**Out of scope for now:** companion-planting advice, seed-saving records, shopping lists, weather-based timing, online barcode lookup (it would send data out).

## Observability and hooks (cross-cutting)
- **Domain event bus**: `emit(event_type, ...)` in `allotment/events.py`. Every state change goes through it. Subscribers: `ActivityLog` writer, Mastodon publisher, metrics counter, structured log line. New behaviour (webhooks, notifications) is added by registering a subscriber. Optional per-allotment outbound webhook subscriber. Measuring adds `measurement.recorded`, `measurement.synced` and `measurements.applied`; the last is recorded in `ActivityLog` and counts as a map edit on the overview.
- **Structured logging**: `structlog` JSON logs in api, worker and beat; `request_id` returned as `X-Request-ID` and propagated into Celery tasks.
- **Metrics**: `/metrics` (Prometheus): HTTP rate/latency by route, domain-event counts; planned Celery task counts/durations, map-job duration, Mastodon post success/failure, DB pool stats.
- **Tracing**: OpenTelemetry (Flask, SQLAlchemy, Celery, Redis, requests) via OTLP when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; frontend will add `traceparent`.
- **Health**: `/healthz` (liveness), `/readyz` (DB, Redis) used by compose healthchecks.
- **Task visibility**: Celery events and Flower in the dev stack; map jobs and Mastodon posts persist status/error text and surface it in the UI.
- **Frontend**: error boundary and client error/web-vitals reporter to `POST /api/v1/telemetry/client`.
- **Dev observability stack** (compose profile `observability`): Prometheus, Grafana, Jaeger.
- **Tests**: events asserted per operation; smoke test for `/metrics`, `/healthz`, `/readyz` and request-ID propagation into a Celery task.

   **Large uploads (AM-23).** Videos from action cameras are huge (a GoPro chapter is up to ~4 GB), so the upload limit is 4096 MB (`MAX_UPLOAD_MB`; the frontend nginx `client_max_body_size` must be at least as large, and streams the body with `proxy_request_buffering off` and hour-long timeouts). Over the limit the server answers 413 while the browser is still sending, which a browser reports as a bare "NetworkError", so `GET /api/v1/limits` tells the Photos page the ceiling and it refuses an oversized file *before* sending, naming the file, its size and the limit; a mid-upload network failure gets an explanatory message too. Uploads use `XMLHttpRequest` for a progress readout (`media/upload.ts`). The API runs gunicorn's threaded worker (1 process, 8 threads, so the in-process Prometheus counters stay right) so one long upload or video stream doesn't block everything else (checked: a 1.2 GB upload finishes in ~12 s while health checks stay under 30 ms); the multipart spool is released as soon as the file has been copied. Peak disk use for an upload is about twice its size (our temp copy plus storage). Not done: chunked/resumable uploads, so a dropped connection restarts the file.
7. **Progress overview**: an event-bus subscriber writes `ActivityLog` rows (task created/completed/reopened, media uploaded, feature changes); `GET /allotments/{id}/overview` aggregates per-day counts (UTC), this/last week, all-time totals, streaks (a day counts if a task was done, a photo added or the map edited; a streak ending yesterday is still alive), latest photos and completed tasks. Dashboard page: headline sentence, stat tiles, heatmap calendar, recent jobs and photos. Only events from now on are logged (no backfill). ✅
8. **Mastodon**: per-allotment account (instance + access token, token Fernet-encrypted and never returned, checked against the instance on save), opt-ins for finished jobs, photos and a daily digest, visibility (unlisted by default; nothing posts until switched on). Event-bus subscribers queue `MastodonPost` rows; the `allotment.send_mastodon_post` task claims a row atomically (no double posts), uploads photos as re-encoded 2560px JPEGs (EXIF and GPS never leave), sends with an `Idempotency-Key`, and on transient errors reschedules itself with backoff (30s, 2m, 8m, 32m; five attempts) while rejected tokens or content fail at once with the reason shown. A burst of photos is folded into one post of up to four pictures (per-allotment advisory lock, `MASTODON_PHOTO_BATCH_SECONDS`); beat runs the daily digest (`MASTODON_DIGEST_HOUR_UTC`, once per day per allotment, only if something happened) and a sweeper that re-queues lost posts. Instance URLs are user input, so https is required and loopback/private addresses and redirects are refused (`FEDIVERSE_ALLOW_PRIVATE_HOSTS=1` for local testing). Settings page: connect/disconnect, test post (sent as `direct`, visible only to the account), post history with status and Retry. Videos are not posted. ✅
   Connecting: in Mastodon, Preferences → Development → New application with scopes `read:accounts`, `write:statuses`, `write:media`; paste the access token into Settings.
9. **Map from media (OpenSfM + GDAL)**: `MapJob` and `MapLayer` models; `POST /map-jobs` takes about 5+ overlapping images (3+ photos with a location; videos count as the frames sampled from them)  and queues `allotment.run_map_job` on a dedicated `mapping` queue, served by the separate `mapper` container (`make mapper`; compose profile `mapping`) so thumbnails and Mastodon posts are never stuck behind it. The worker image (`worker/Dockerfile`, Ubuntu 24.04) compiles OpenSfM from a pinned commit into its own virtualenv and runs it as a subprocess; the app only reads its JSON. Pipeline: dataset prep (photo locations written as `exif_overrides`, all at the stated camera height because phone altitude is unreliable; **video frames get no GPS**, see below) -> `extract_metadata, detect_features, match_features, create_tracks, reconstruct, undistort` -> ground plane fitted to the sparse points (plants poking up are rejected) -> every photo's pixels cast onto that plane to give GCPs (`mapping_geo.py`, plain numpy and unit-tested) -> GDAL: `gdal_translate -gcp` per photo, one `gdalwarp -tps` mosaic (nearest photos drawn last), `gdal2tiles --xyz`. Tiles live in storage under `allotments/{id}/layers/{layer}/tiles/z/x/y.png` and are served through signed, expiring links (an `<img>` can't send a bearer token); a missing tile returns a blank PNG. The job log tail, stage, cancel (queued at once, running within ~10 s) and failure reasons are persisted and shown in the UI. Layers page: list, show/hide, opacity, delete; build form with the same readiness rules as the server; recent builds with progress. Visible layers are drawn on the map under the shapes. `layer.created` counts as a map edit on the overview. The worker image is built and pushed by the `build` workflow (`allotment-worker`).

   **Videos (AM-21).** Upload already handled video (AM-6); the map builder now uses it. A video is sampled at about 1 frame/s, spread over its whole length if that would exceed 60 frames, and in each interval the sharpest of three candidate frames is kept (hand-held video blurs). Frames deliberately carry **no location**: a video has one (its start), and pinning every frame to it would drag the map together, so frames are placed by matching them to the geotagged photos, and those photos still fix position and scale (3+ are required; a video alone can't place a map). OpenSfM switches off GPS-based pair selection as soon as any image lacks GPS and would then try every pair, so datasets with video use neighbouring-frame (`matching_order_neighbors`) plus bag-of-words matching across cameras (`matching_bow_neighbors`, `matching_bow_other_cameras`); each video gets its own camera model. The API and the Layers page count a video as its estimated frames against the 150-image limit (`mapping_video.py`, mirrored in `maps/status.ts`). `SCENARIO=video make mapping-check` walks a GPS-less camera over the edges of a plot that nine photos cover in the middle: all frames are placed, the map grows from about 25 x 19 m to 45 x 32 m, and the video-only part lines up with the true texture and agrees with the photo part to ~0.2 m. Because only the photos anchor scale, a video-heavy map with few photos inherits the GPS scale error (a few percent with phone-quality GPS), so take photos around the edges of the plot with location on. Not done: per-frame GPS from camera telemetry (GoPro/DJI), skipping near-duplicate frames when the camera stands still, in-browser transcoding of HEVC (AM-15).
   **Recognising objects (AM-25).** The stitched overlay is unusable for hand-held photos (every photo's far ground and every tall thing gets smeared along its viewing rays onto a flat plane: a spiky mess), and it was never what was wanted. What the map needs is *recognition*: find the sheds, water butts, trees and compost bins and draw them as labelled shapes. A job now makes recognised objects (default) and/or the overlay (opt-in, experimental, layer hidden by default). Pipeline, after OpenSfM has the camera poses: pick up to 40 placed photos (real photos first, video frames fill the rest) -> a local open-vocabulary detector (Grounding DINO tiny) finds objects from text prompts and SAM outlines each one (CPU, about 15 s per photo; weights download into the `models` volume on first use, because they are too big for a registry layer) -> each mask's *contact line* (lowest pixel per column) is cast onto the fitted ground plane to get position and width (`detection_geo.py`); depth is a guess (round things as deep as wide, boxes 0.7 x), which averages out when several photos see an object from different sides -> detections of the same kind that land together are merged (weighted by distance and score) -> dropped if beyond 15 m, an implausible size for the type, or seen in only one photo without confidence -> stored as `MapSuggestion` rows with a kind, a name ("Water butt 2"), a Point + radius or a Polygon, confidence and how many photos saw it. The Map page shows them as dashed labelled shapes with a review panel: tick, rename, change the type, then "Add n to the map" (all-or-nothing, creates ordinary features) or dismiss. Nothing reaches the map unreviewed, and a re-run replaces earlier pending suggestions. Beds, paths and other shapeless areas are not found by an object detector and are still drawn by hand.
   **The plot's boundary (AM-26).** The same pass also looks for fence posts and fences. Each post (the foot of its mask) and each fence (points along its foot) is put on the ground plane, giving a cloud of fence points. `boundary.py` fits the outline to it: RANSAC finds long straight lines (points are not consumed, because a corner post belongs to two sides; a near-parallel line that mostly re-uses a stronger line's points is an echo and is dropped); the strongest sets the plot's direction and only lines along or across it (within 12 degrees) are kept, which ignores diagonal fences; then on each of the four sides the *nearest line beyond everything known to be inside the plot* (where the cameras stood, plus the objects found) is taken. That rule skips a fence cutting through the plot (cameras on both sides of it) and prefers the plot's own fence over a neighbour's further out. A side with no such line is guessed from how far the photographed area reaches plus 1.5 m, and the result says how many sides were real. It is offered as a `boundary` polygon suggestion: "Plot boundary" with 3 or 4 fenced sides (ticked by default), "Plot boundary (rough)" with 2 (not ticked), nothing with fewer. The ground plane is now fitted only to points below the cameras' height and limited to a 25% tilt (a hand-held reconstruction is mostly tall far-away things, and the first real run put the "ground" 0.3 m under the cameras and mis-scaled everything fivefold).
   **What the real photos showed (AM-26).** A real set (18 Pixel photos, all with the *same* GPS fix, although they were taken walking round the boundary (the phone's location never updated), plus a GoPro walk) taught three things. (1) The sparse point cloud OpenSfM returns is mostly far-off things at about camera height (horizon, trees, other plots) with almost nothing on the nearby grass, so a ground plane fitted to it sits near the cameras and its height varies between runs (0.4 to 1.6 m under the cameras): the fit now ignores points above the cameras and rejects steep tilts, a badly tilted reconstruction is stood upright from the cameras' average "up" (`geo.level`), and the piece with the located photos is chosen. (2) Because the photos are taken from one spot there is no parallax, so a detection-agreement self-calibration of the ground height (`calibration.py`: the right height is a sharp peak where detections from different photos coincide; verified on synthetic scenes whose scale is wrong by 0.25x to 5x, and it correctly refuses random data) finds no peak on such photos and falls back to the cloud; it exists for captures that *do* move (a video walk). (3) Where things are relative to the camera does not need the scale at all: the ground distance to the foot of an object seen from a camera held at height h is h / tan(angle below the horizon), in metres; only the relative positions of cameras that are far apart depend on the scale, and for photos from one spot that error is small. Fence posts and fence feet are detected and fitted, but on this plot (fences, hedges, mesh, bins and neighbours' posts at every distance, the farther ones smeared by a degree of pitch error) the points form a diffuse scatter and **no trustworthy outline came out, so none is proposed**: the fit declines rather than invent a rectangle. It does recover plots in synthetic scenes (neighbour and internal fences ignored, missing sides guessed and flagged). A capture that would work: walk the plot's inside edge keeping the fence in view, or take a photo along each fence from each corner. Also fixed here: `pyproject.toml` listed only the top-level package, so a wheel left out `allotment.api` (images worked only because they run from the source directory).
   **Video telemetry and stuck GPS (AM-22).** A GoPro records a GPS track in its GPMF data stream (`gpmd`, about 18 fixes a second). `video_telemetry.py` pulls that stream out with ffmpeg, parses the GPS5 blocks (dropping poor fixes: fix below 2D or DOP over 5) and times them by spreading each one-second block over the video; a frame's position is the median of fixes within half a second, so jitter and one-off outliers are smoothed out. A track that never leaves a 5 m box is ignored. Located frames go into `exif_overrides` like photos (at the stated carrying height), so a video alone can now place and scale a map, and a located walk gives OpenSfM real parallax to scale from. Phone videos and other cameras have no readable track and behave as before (DJI subtitles and Android timed metadata are not read; a fixed-speed fallback was not built). Two related guards: frames that repeat the previous one (mean grey difference under 2/255, a camera that stopped) are skipped before matching, and **photos whose GPS is stuck** (4+ photos at one place over more than a minute, as when a phone never updates its location) are not given a position at all, because trusting them pins the map to a point. Real check on the Pixel photos plus GoPro walk: all 60 sampled frames were located, the 19 stuck stills were ignored, the largest reconstructed piece went from under 1 m across to 29 x 17 m with 26 photos, and the scale came out consistent (0.75) instead of swinging between 2.3 and 16.6. It still found no plot boundary (24 fence points, too scattered), so the outline remains something to draw or to trace with the planned mobile app. Still not done: per-frame positions need a clock offset if photos are to be located by timestamp against the video track.
   **Fixing scale and heading when GPS can't (AM-25).** OpenSfM scales and orients a reconstruction by fitting camera positions to the photos' GPS, which says nothing when the photos were taken from one spot: a real set of 18 Pixel photos all carried the *same* GPS fix, and an earlier run came out about five times too small (a 7 cm "water butt"). When the cameras are within 20 m of each other the scale is therefore set from how high the camera was held (`camera_height_m` against the camera heights above the fitted ground plane), and the heading from the phones' compass headings when at least four agree (circular mean, agreement above 0.6, only when the cameras are within 15 m). Both are logged on the job. OpenSfM also returns several disconnected pieces, and only a piece containing located photos is aligned to the real world, so the piece with the most located photos is used (at least three, else a clear error). Verified against synthetic scenes with known objects (positions within ~0.3 m for round objects, a wrong scale of 5x recovered) and by running real photos through the real models; positions rest on the pose quality, which for sparse hand-held photos is limited (about half of a typical set links up).
   **Accuracy and limits.** The model is a flat ground plane (a fitted, possibly tilted plane), so hills, tall objects and very oblique shots distort; ground further than 12 camera heights away is ignored. Position and, importantly, **scale come from the photos' GPS**: phone jitter of 1-3 m across a plot shows up as a scale error of about 1-4% (checked: 0.3 m noise gives ~1%, 1.5 m noise gives ~4%, with position within 0.5 m either way). The map is shape-consistent but should be corrected with a measured distance; that is what the measuring checklist (phase 11) and ticket AM-18 are for. `make mapping-check` renders a textured ground plane from 25 GPS-tagged overhead cameras, runs it through the real pipeline and compares the tiles with the known texture (scale and rotation scans, offset, correlation). It is not in CI because it needs the 3.5 GB worker image. Real hand-held photos have only been checked through this synthetic scene.
